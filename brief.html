Hands-on product review · NVIDIA NeMo Relay 0.11.1

NeMo Relay Through the Eyes of Its Users

A customer- and developer-experience review: who Relay serves, where the experience delights, where it breaks, and what I'd build next.

Nimish Singhal · Senior Technical Product Manager – AI Agents (JR2029528) candidate · November 10, 2026

TL;DR. I started with one product question: Relay serves everyone who touches an agent, not just developers, so can it understand who is behind a request and what context it's in? Nous Research's enterprise fleet demo made that concrete: personal agents need privacy, shared agents need full records. I built a small two-agent fleet on Relay 0.11.1 and ran eight experiments.

Finding: Relay can do it. Its scope-local sanitizers produced a personal agent with zero content but full token metrics across all five export formats. But the correct path is hard to find: 2 of my 3 attempts silently leaked content or lost metrics, and the defaults suggest a privacy that isn't there.

Why it matters for evals: most real agent usage is personal. In an eighth experiment I A/B-tested a harness change using only content-free telemetry: zero content exported, yet tokens, tool calls and compaction were fully measurable (synthetic data by design: the point is the measurement). But the fence silently deleted the pass/fail label too. Privacy and evals have to be designed together.

Recommendation: make the easy path the correct path, with honest defaults, then declarative privacy presets, owner/tier context set when an agent starts, and an eval-signal channel that survives privacy fences. That removes the same friction for every partner that embeds Relay, and lets evals cover the whole fleet, not just shared agents.

1. The question I started with

Relay sits on every model call and tool call an agent makes. That makes it the one place in the stack that can see who is acting, what they're doing, and how sensitive it is.

Agents are no longer used only by engineers. A PM using Claude Code, a CFO with a morning-briefing agent, and a platform engineer debugging a harness all produce the same kind of event stream. So the product question isn't "how do we trace calls?" It's:

Can Relay understand the user and the context of each request well enough to give each person the right protection, explanation and optimization?

As a platform principle, I'd put it this way: Relay should carry context, not interpret it. The core standardizes identity, role, tier and sensitivity on every event. Partners and plugins decide what to do with it. A neutral standard that carries context is what scales across an ecosystem-led go-to-market.

3. What the Nous Research demo revealed

In NVIDIA's Inside Hermes Agent Traces with NeMo Relay livestream, Nous Research's lead enterprise engineer described what changes when agents go from personal tools to managed fleets. Three ideas shaped this review (paraphrased from the auto-generated transcript):

IdeaWhat it means for Relay's users
The user/operator splitOn a personal agent, you are user and operator. In a fleet, employees use agents while IT configures them and AI teams tune them. "The CFO doesn't want to see the errors." Different people need different views of the same run.
"The same log is three things"One trace is eval and training data, an employee's personal work data ("almost reading their email"), and company IP. What to keep depends on whose agent it is and what's in the request.
Four layers of observabilityL1 health (no content) → L2 analytics (tokens and tool names, no content) → L3 audit (varies by company) → L4 full trajectories. Personal agents are fenced to about L2, shared agents keep L4. Today Nous enforces that fence downstream, in its OpenTelemetry collector.
❓ The question this raised: If every partner has to rebuild Nous's fence in its own collector, can Relay enforce it at the source, before content ever leaves the agent process?

6. Findings by persona

App developer and partner integrator: developer experience

WorksFast, clean first trace. Strict config validation with precise errors (e.g., field 'sinks' is not recognized for 'atif'). Negligible overhead.
WorksScope-local primitives are powerful. Rules attached to one agent apply to its whole subtree, including subagents.
FrictionThe correct privacy path is not the obvious one. Generic event sanitizers (the first tool I reached for) either leaked the normalized prompt into ATIF (v1) or wiped token metrics from ATIF and every OTel projection (v2). Only the native LLM/tool sanitizers (v3) got it right.
EffortThe correct fence took 5 callbacks across 3 registries, plus knowledge of the provider's response shape. Mine is OpenAI-chat-specific, so a multi-provider partner needs one per codec.
DocsDocs on main run ahead of the published release, so the first run fails.

IT operator: running the fleet

GapNo declarative privacy tier. PII rules target JSON paths in payloads, not an agent, owner or deployment unit. Tiering is code, not configuration.
GapThe gen_ai projection, which Relay adds automatically when OTEL_EXPORTER_OTLP_ENDPOINT is set, emits GenAI semantic conventions only and dropped my owner/privacy_tier labels. A collector-side fence can't route on them. (full and openinference kept them.)
GapThe agent's own start event can't receive injected context, because injectors register after the scope opens.
WorksCorrect parent/child attribution with two agents and their subagents interleaving.

AI team: improving agents

WorksVictor's L2 tier is achievable. With the native path, the personal agent exported token counts (gen_ai.usage.*, llm.token_count.*), tool names, timing and full ATIF step metrics with zero content. AI teams can tune skills without reading employee data.

Employee: trust

RiskDefaults suggest privacy that isn't there. With enable_full_payloads = false, the event log still held the prompt, response, tool arguments and results. The flag only stops repeating earlier conversation turns.
RiskBuilt-in PII redaction caught email and card numbers. A name ("bob smith") passed through, and so did the phone number, since that detector wasn't enabled. Output had a formatting slip: card [REDACTED]and call me.

Compliance and leadership: proof of control

WorksThe destructive command was blocked before it ran, and the guardrail check is recorded as its own auditable event.
GapThe record shows the rejection reason, but nothing about what was attempted. That's privacy-safe, but auditors will ask.
⚠️ A correction, kept on purpose: After experiment 6, I believed Relay couldn't keep token metrics for a content-free agent. Experiment 7 proved me wrong: the native sanitizers do it. I've kept this visible because it is the finding. A motivated PM with a coding agent took three attempts to find the right path, and partners will hit the same wall.

Also observed: Relay adds an x-dynamo-session-id header to model requests by default, a built-in link to NVIDIA Dynamo serving.

7. From privacy to evals: the harness loop

Relay's deepest value isn't recording runs. It's helping people make agents better: observe a run, evaluate it, change the harness, and measure again.

flowchart LR R["Agent runs
(personal + shared)"] --> T["Relay telemetry
(fenced by tier)"] T --> E["Evaluate
success + cost + behavior"] E --> C["Change harness
skill, prompt, model, tool"] C --> R

Figure 3. The harness loop. If personal agents can't enter it, evals only ever see a fraction of real usage.

NVIDIA's own Hermes ToolPerf benchmark shows why behavior matters as much as success: a set of harness fixes lifted Qwen's success from 70% to 81% but cost 29% more LLM calls, about 2× the data, and 56% more latency. On the livestream, Patrick found a local model "passing" while it web-searched and compacted repeatedly instead of reading a skill.

Experiment 8 re-created Patrick's case synthetically: a baseline harness that web-searches versus a skill-first harness, 15 runs each. Every run was a personal agent behind the native privacy fence, with a canary secret planted in every prompt, response and tool result.

Canary content exported: 0, in ATOF and in all 30 ATIF trajectories. Values are synthetic by construction; what the experiment demonstrates is the measurement, not a real harness result.

✅ What works: A harness change can be evaluated on personal agents with zero content. Pass rates sit within noise while tokens differ about 4.5×, exactly the kind of trade-off success metrics hide. This is Victor's "you don't need content to make some of those decisions," made measurable.
⛔ What breaks: When I recorded pass/fail in the event's data, the obvious place, the privacy fence silently deleted it along with the content. Only a copy in metadata survived. Arm attribution also worked only because I passed it as scope metadata at creation. Today there's no defined channel for labels and scores that should pass a privacy fence.

The product insight: privacy and evals are usually owned by different teams, but in Relay they're the same pipeline. A fence designed without evals blinds the AI team, and an eval design without privacy can't touch personal agents. Relay is the one layer that can serve both, if it ships them together.

10. What I didn't test

  • Synthetic data only: mock model and tool callbacks, one provider shape (OpenAI Chat). Real streaming, large payloads and multiple providers may behave differently. The harness A/B outcomes are simulated; only the measurement is real.
  • Not exercised: the Claude Code/Codex gateway, a live OTLP backend, adaptive tuning and caching (ACG, response cache, hints), the daemon, and streaming responses.
  • Attribution was tested with explicit scope handles, not the implicit scope stack.
  • Livestream quotes are paraphrased from an auto-generated transcript.
  • The team may already be tracking some of these. I offer them as what a partner will hit, not what was missed.
